# Архитектура

Как устроен бот внутри. Установка — [`SETUP.md`](SETUP.md), эксплуатация —
[`OPERATIONS.md`](OPERATIONS.md), экраны — [`SCREENS.md`](SCREENS.md), правила
и значения по умолчанию — [`RULES.md`](RULES.md), почему сделано именно так —
[`DESIGN-DECISIONS.md`](DESIGN-DECISIONS.md). Номера разделов этого документа
упоминаются в комментариях кода, поэтому при правке их не сдвигают.

## 1. Главные принципы

1. **Сырьё отдельно от интерпретации.** Журнал апдейтов Telegram пишется всегда и не правится.
   Сторона, автор, вердикт ИИ, обращения, просрочки — производные, их можно снести и пересчитать.
   Поэтому ошибку парсера или правила можно чинить задним числом.
2. **Приём не зависит от ИИ.** Процесс `bot` только принимает апдейты и отвечает на кнопки.
   Всё тяжёлое и внешнее делает `worker`. Упавший провайдер не останавливает сбор данных.
3. **Обращения пересобираются целиком каждую минуту.** Правка логики движка не требует
   миграции данных: следующий тик применит её ко всей истории. Чтобы переход на новые
   правила не переписывал прошлые отчёты, у правил есть версии с датой перехода (раздел 7.3),
   а у настроек сроков — история версий (раздел 7.5). Правка внутри версии действует
   на всю её историю.
4. **Бот не пишет в клиентские группы.** Это держит заслон на HTTP-слое, а не дисциплина
   в обработчиках (раздел 11).

## 2. Процессы

| Процесс | Точка входа | Что делает |
|---|---|---|
| bot | `app/bot/main.py` | long polling; журнал апдейтов; приём сообщений групп; меню и экраны в личке |
| worker | `app/worker/main.py` | тик раз в 60 с: классификация, пересборка обращений, алерты, рассылки, суточные задачи |
| migrate | `alembic upgrade head` | миграции при каждом старте compose |

Оба процесса собираются из одного образа. База — PostgreSQL 16 в том же compose.
Конфигурация — переменные окружения (`app/config.py`), бизнес-настройки — таблица `setting`,
меняются кнопками в боте.

**Порядок шагов тика worker** (`run_once`):

1. `reprocess_edited` — у правленых сообщений стираются вердикт и атрибуция, сообщение
   возвращается в очередь (до 50 за тик).
2. Если `AI_ENABLED` и ключ заданы: проба основной модели в режиме резерва, `classify_pending`,
   бесплатная проба провайдера в простое, учёт здоровья ИИ и уведомления о сбое и медленной работе.
3. `rebuild_interactions` — пересборка всех обращений.
4. Раз в сутки: очистка по срокам хранения, повтор упавших апдейтов, пересчёт наблюдаемых ролей сотрудников.
5. Отметка живости для healthcheck.
6. Если алерты не на паузе: досылка недоставленных, новые алерты, зачёркивание закрытых.
7. Рассылки: досылка выпусков, вечерняя сводка, недельный и месячный отчёты, сводка по алертам,
   напоминание о привязке учёток.
8. Пульс в базе (`setting['uptime_runtime']`) — по нему следующий старт узнаёт о простое.

Ошибка тика пишется в лог (`worker.tick_failed`), процесс не падает. Тик длиннее 30 с —
предупреждение `worker.tick_slow`: признак того, что полная пересборка перестаёт помещаться в минуту.

## 3. Модель данных

Описание — `app/db/models.py`, миграции — `alembic/versions/`. Текущая ревизия `0c8570914f56`.

**Сырьё**

| Таблица | Назначение |
|---|---|
| `telegram_update` | неизменяемый журнал апдейтов, ключ `update_id` (идемпотентность при повторной доставке); `processed_at`, `processing_error` |

**Чаты и сообщения**

| Таблица | Назначение |
|---|---|
| `chat` | групповой чат: `tg_chat_id`, название, состояние (discovered / tracked / paused / archived), `tracked_since` |
| `chat_tracking_period` | интервалы, когда чат был в анализе; открытый интервал на чат один (частичный уникальный индекс) |
| `chat_title_history` | история названий чата |
| `message` | проекция сообщения: текст, вложение, ветка форума, `transport_actor_kind` (кто прислал по Telegram ID), `business_side` (чья сторона), `side_rule_version`, `needs_reclassification`; уникальность `(chat_id, tg_message_id)` |

**Люди**

| Таблица | Назначение |
|---|---|
| `staff` | справочник сотрудников: имя, нормализованное имя + различитель (уникальны вместе), `tg_user_id`, период работы, роль менеджер/специалист и её источник (auto / manual) |
| `staff_alias` | варианты написания имени; уникальность держит индекс |
| `attribution` | автор сообщения компании: `staff_id` (NULL — не определён), метод (exact / tg_id / manual), `parser_version`, кто разметил вручную |
| `sender_rule` | решение человека «кто это» про отправителя: вид (tg_user / bot / anonymous_admin), Telegram ID, чат (только для анонимного админа), сторона, сотрудник |
| `bot_user` | учётки бота: роль, персональные права поверх роли, состояние (pending / active / disabled), привязка к сотруднику, флаг «уведомления в личку» |
| `invite_code` | одноразовые приглашения; хранится только sha256 кода |
| `audit_log` | действия людей, влияющие на чужие данные: роли, чаты, настройки, снятия нарушений, разметка |

**Производное и служебное**

| Таблица | Назначение |
|---|---|
| `classification` | вердикт ИИ или правила по сообщению: модель, `prompt_version`, источник (rule / model / technical), метка, `requires_response`, `is_substantive`, `answers_request_id`, ошибка, число попыток; уникальность `(message_id, model, prompt_version)` |
| `interaction` | обращение клиента: открывающее сообщение, первая реакция, передача специалисту, ответ, состояние, время в календарных и рабочих секундах, признаки просрочки по двум слоям, версия правил |
| `ai_usage` | расход токенов по дням и моделям |
| `alert_log` | журнал алертов: ключ `(chat_id, opened_by_message_id, kind)`, получатели, доставка и попытки, id отправленных сообщений и текст (для зачёркивания), `covered_by_id`, `shadow` (прежний теневой режим; новые записи — `false`) |
| `breach_dismissal` | решения «снять нарушение», ключ `(chat_id, opened_by_message_id)` |
| `setting` | бизнес-настройки разделами (JSON) и служебные состояния: `ai_health`, `uptime_runtime`, `reprocess_state`, `attribution_marks`, состояния рассылок |

Почему ключ алертов и снятий — открывающее сообщение, а не id обращения: обращения
пересоздаются каждый тик, их id меняются, открывающее сообщение стабильно.

## 4. Путь сообщения

```
Telegram → bot: telegram_update (журнал) → message (проекция, сторона) → attribution (автор)
        → worker: classification (ИИ) → interaction (обращения) → alert_log (алерт) → сводки
```

1. **Журнал.** Middleware бота пишет апдейт в `telegram_update` до обработчиков.
   Дубль `update_id` отбрасывается. Ошибка обработчика пишется в `processing_error`;
   раз в сутки worker переигрывает упавшие апдейты (нажатия кнопок — никогда).
2. **Проекция** (`services/ingestion.py`). Новый чат заводится сам (в анализ сразу или
   в «обнаруженные» — по настройке). Сообщение upsert'ится по `(chat_id, tg_message_id)`.
   Правка обновляет текст, ставит `needs_reclassification` и пересчитывает сторону.
   Служебные события Telegram распознаются по белому списку полей: новый тип события
   по умолчанию служебный. Группа уведомлений не сохраняется вовсе.
3. **Сторона и автор** (раздел 5) — сразу при приёме, без внешних вызовов.
4. **Классификация** (раздел 6) — в worker, очередью.
5. **Обращения** (раздел 7) — пересборка каждый тик из сообщений и вердиктов.
6. **Алерты и сводки** (раздел 8).

## 5. Сторона и автор

Сотрудники пишут из Bitrix24, в Telegram сообщение приходит от бота-интегратора
с подписью «Имя Фамилия [домен] пишет:». Бот-интегратор один на всех, поэтому автор
определяется только разбором текста.

**Кто прислал** (`resolve_transport_actor`) — только по `from.id` и признаку бота:
система Telegram, интегратор (`INTEGRATOR_BOT_ID`), чужой бот, человек.

**Чья сторона** (`resolve_business_side`), по порядку:

1. событие Telegram — не определено;
2. правило отправителя из `sender_rule` (решение человека сильнее кода);
3. анонимный админ группы («от имени группы») — компания;
4. интегратор: служебный ответ (маркеры в начале текста) — система; подпись с пометкой «(К)» —
   клиент (так интегратор приносит людей клиента); иначе — компания;
5. человек: есть в справочнике по `tg_user_id` или это активная учётка бота
   (или учётка, привязанная к сотруднику) — компания; иначе — клиент.
   Учётка в ожидании не в счёт: `/start` может нажать и клиент;
6. прочие боты — не определено.

Правило версионировано (`SIDE_RULE_VERSION = 5`, пишется в `message.side_rule_version`).
При старте worker сверяет пару «ID интегратора + версия правила» с сохранённой
(`reprocess.sync_integrator_change`). Если что-то изменилось, стороны всей истории пересчитываются,
у сообщений, перешедших клиент↔компания, стирается вердикт (он получен не тем промптом).

**Автор-сотрудник** (`services/attribution.py`, `PARSER_VERSION = 2`): точное совпадение
нормализованного имени или варианта написания; затем совпадение без учёта порядка слов,
если человек один; затем новый сотрудник заводится в справочник автоматически из подписи.
Подпись, помеченная «не сотрудник», и шаблоны текстов без подписи дают «автора нет» с методом
manual. Для сообщений людей напрямую — правило отправителя, `staff.tg_user_id` или привязка учётки.
Строки с методом manual автоматика не перезаписывает никогда.

**Разметка «кто это»** (`services/sender_rules.py`). Единица разметки — отправитель, а не
сообщение: решение действует на всю его переписку, прошлую и будущую. `apply_rule` —
единственное место, меняющее данные по правилу. Для анонимного админа правило действует
в одном чате: за служебной учёткой Telegram в каждом чате стоит свой человек.

## 6. Классификация ИИ

**Клиент** — `AiClient` в `services/ai.py`, OpenAI-совместимый `POST {AI_BASE_URL}/chat/completions`.
Провайдер меняется переменными окружения. Прошлая разметка остаётся действительной, пока модель
есть в `AI_PREVIOUS_MODELS` (или это резервная модель).

**Что уходит провайдеру.** Системный промпт профиля (для клиента и для компании свои) и три блока:

- до 6 предыдущих событий чата строго раньше текущего (`[ДД.ММ ЧЧ:ММ] клиент|компания: текст`,
  вложения маркерами `[документ]`, `[фото]` и т. п.; рассылки и служебные ответы исключены);
- до 3 открытых обращений чата с внутренним номером и состоянием (строятся повтором движка в памяти);
- само сообщение.

Будущие сообщения не подаются никогда: иначе переспрос переписывал бы разметку прошлого.
Названия чатов и Telegram ID не уходят. Текст уходит как есть, вместе с подписью интегратора
(имя сотрудника).

**Метки.** Клиент: `request`, `question`, `answer`, `addition`, `correction`, `mixed_request`,
`ack`, `social`, `offline` (+ устаревшая `info`). `requires_response` выводится из метки.
Компания: `substantive`, `handoff`, `promise`, `question`, `ack`, `other` и `answers_request_id` —
номер открытого обращения, на которое отвечает реплика (принимается только номер из поданного списка).

**Очередь** (`worker.classify_pending`, условия общие с экраном состояния в `services/ai_stats.py`):
сообщения клиента и компании с текстом, в чатах в анализе (или помеченные на переспрос),
без действительного вердикта. До 20 сообщений за проход, дедлайн прохода 150 с.
Порядок — по времени; сообщение не отдаётся, пока в том же чате висит более раннее с ошибкой:
контекст следующего зависит от вердикта предыдущего. Часть сообщений клиента размечает правило
без ИИ (`rule_based_client` в `worker/main.py`, `source='rule'`): «спасибо», «ок», «👍» и подобные —
`ack`, любое сообщение не длиннее двух символов после обрезки пробелов («да», «??», «10») — `social`;
оба без `requires_response`. Проход разбит на три части: выборка в короткой
транзакции, сетевые вызовы без транзакции, запись каждого вердикта отдельной транзакцией.

**Повторы.** Отказ по сообщению повторяется через 5 и 15 минут, третья попытка идёт на резервную
модель. После трёх отказов пишется технический вердикт (`source='technical'`): движок его не читает,
но чат перестаёт блокироваться. Таймаут вызова `AI_TIMEOUT_SECONDS` (60 с).

**Промпт-профили** (`PROMPT_PROFILES`). Профиль — тексты плюс параметры вызова; выбирается
`AI_PROMPT_PROFILE`, иначе по имени модели. В `classification.prompt_version` пишется номер профиля
(`gptoss-p14` — 1502, `deepseek-ds1b` — 1402). Для gpt-oss параметр `reasoning_effort` передаётся
верхним полем тела: вложенный объект `reasoning` провайдер игнорирует, и модель тратит лимит токенов
на рассуждения, возвращая пустой ответ. Отпечатки текстов держат тесты.

**Резерв и размыкатель** (`FallbackCircuit`). Три отказа основной модели за 5 минут переводят
классификацию на `AI_FALLBACK_MODEL` с её собственным профилем. В режиме резерва раз в 30 минут
идёт платная минимальная проба основной; две удачные пробы подряд возвращают основную.
Состояние размыкателя живёт в памяти процесса, пороги — `AI_FALLBACK_*`.
Известное различие профилей: резервный `deepseek-ds1b` размечает просьбу позвонить меткой `request`,
основной `gptoss-p14` — меткой `offline`; движок открывает обращение по `offline` только при прямой
просьбе связаться (§7.4), поэтому на резерве просьбы о звонке чаще становятся обращениями.

**Месячный потолок** (`AI_MONTHLY_TOKEN_LIMIT`). Перед каждым вызовом проверяется, что сумма
токенов месяца из `ai_usage` плюс оценка запроса не превысит потолок. Иначе вызов не отправляется,
здоровье ИИ сразу переходит в «сбой», алерты встают на паузу. Расход пишется и за битые ответы.

**Режимы.** `AI_ENABLED=false` — ИИ не вызывается и правила тоже; обращения строятся
на неразмеченных сообщениях. `AI_SHADOW_MODE=true` — модель вызывается и вердикты пишутся,
но движок учитывает только вердикты правил: вердикты модели на обращения и алерты не влияют.
В коде по умолчанию `true`, поэтому в рабочем `.env` переменная задаётся явно: `AI_SHADOW_MODE=false`.

**Состояние ИИ** (`services/ai_health.py`, `setting['ai_health']`):

- «сбой»: 3 неудачных прохода подряд или исчерпан потолок; алерты на паузе, иначе без вердиктов
  пошёл бы поток ложных тревог. Сообщение ответственным на вход и на выход, с распознанной
  причиной (истёк ключ, баланс, модель пропала, сеть, наш потолок);
- «частичный сбой»: не меньше половины неудач в последних 10 проходах; только строка на экране;
- «медленно»: медиана задержки выше `AI_SLOW_LATENCY_SECONDS` или очередь старше
  `AI_SLOW_QUEUE_MINUTES`; отдельные уведомления, алерты не глушатся;
- «на резерве»: работает резервная модель; алерты не глушатся;
- если 30 минут не было контакта с провайдером, worker сам делает бесплатный `GET /models`
  и проверяет, что модель есть в каталоге.

## 7. Движок обращений

Код — `services/episodes.py`, функция `rebuild_interactions`. Сроки — `services/calendar.py`.

### 7.1 Обращение и два слоя

Обращение открывает сообщение клиента, требующее ответа. Дальше:

- **первый слой — реакция.** Любая реплика компании, считающаяся реакцией, фиксирует
  `first_reaction_at`. Срок — `response_deadline`: порог в рабочих минутах (30); если до конца
  рабочего дня не помещается, в следующий рабочий день порог даётся целиком заново;
- **второй слой — специалист.** Если реакцией была передача специалисту (`handoff`), открывается
  ожидание специалиста со сроком «то же время следующего рабочего дня» от передачи
  (`same_time_next_workday`). Закрывает его выход специалиста на связь: ответ по существу,
  встречный вопрос клиенту, реплика другого сотрудника (по правилам ниже). Нет передачи —
  обращение закрыто первым слоем: помощник ответил сам.

Состояния: `open` (реакции нет), `reacted` (ждёт специалиста), `answered`, `no_response_needed`
(ни одно сообщение клиента ответа не требовало), `abandoned` (окно ожидания истекло без ответа:
24 часа после срока первого слоя или 7 суток после срока второго). Метрики хранятся в календарных
и рабочих секундах (`ttfr_*`, `ttfa_*`); признаки `sla_breached` и `substantive_breached`
считаются один раз здесь, и отчёты читают их, а не пересчитывают: иначе отчёт разошёлся бы с алертами.

Файл от сотрудника (документ, фото, видео, аудио) — ответ по существу независимо от подписи.
Служебные ответы интегратора (`transport_notices.py`) и рассылки — одинаковое тело длиннее 60 символов
в 3+ чатах за 10 минут (`broadcasts.py`) — реакцией не считаются.

### 7.2 Окно «ждём клиента» и «ждём материал»

Вопрос или просьба компании (метка `question` или реплика, кончающаяся «?») взводит окно
до того же времени следующего рабочего дня. Реплика клиента в окне — ответ, а не новое обращение
со сроком. В v4 окно не гаснет от первой реплики клиента. Открыть обращение внутри окна может:

- реплика со знаком вопроса или с меткой `mixed_request`;
- просьба позвонить или связаться («перезвоните», «свяжитесь»);
- поручение: повелительное наклонение («загрузите пп в банк»), «прошу/просьба» или «нужно + глагол».
  «Давайте» при этом — согласие на предложение компании («Да, давайте сделаем», «давайте
  в битрикс»), а не поручение;
- вопросительное слово без «?» («почему так», «подскажите») при метке `question`.

Реплика компании с меткой `other` или одно приветствие окно не гасят и не взводят.

**Ждём материал.** Просьба компании прислать материал в чат — «пришлите», «загрузите», «прошу
прислать», разговорные «давайте сюда», «присылайте», «скидывайте», «кидайте» — взводит отдельное
состояние до того же времени следующего рабочего дня: вложения клиента без текста и короткие
подписи к ним (`answer`, `ack`, `info`) — ответ, а не обращение; текстовые просьбы и вопросы
судятся как обычно. Просьба прислать на почту состояние не взводит: материал в чат не придёт.

### 7.3 Версии правил

Версия обращения (`interaction.version`) определяется моментом его открытия относительно
`EPISODE_RULES_V2_SINCE`, `V3_SINCE`, `V4_SINCE`. Обращение, открытое до границы, целиком живёт
по старым правилам: опубликованная история не переписывается. Границы не сдвигают.

- **v1** — одно открытое обращение на ветку чата; новая просьба после реакции без передачи
  открывает новое обращение.
- **v2** — служебные ответы и рассылки не реакция; неопределённый автор компании — реакция
  (в личную статистику не идёт); окно «ждём клиента».
- **v3** — новая просьба во время ожидания специалиста получает своё обращение.
- **v4** (включает v2 и v3) — правила ниже (§7.4). Обращение v4, закрытое веткой старых
  правил, не воскресает. Новой установке достаточно задать `EPISODE_RULES_V4_SINCE`
  моментом раньше первого сообщения; если все три границы пусты, действует v1.

Редакция правил движка — константа `ENGINE_RULES_REVISION` в `episodes.py`; она пишется в лог старта
worker (`worker.starting`, поле `engine`). Правила действуют на всю историю v4: worker каждым тиком
пересобирает обращения из сообщений и вердиктов.

### 7.4 Правила v4

**Первый слой — реакция.**

- До первой реакции каждая просьба клиента получает своё обращение и свой срок.
- Реакция — любая реплика сотрудника, кроме одного приветствия, служебных ответов и рассылок.
  Реплика с меткой `other` (не о работе клиента: «с завтрашнего дня я в отпуске») тоже нарушает
  молчание — это первая реакция, но не ответ: ничего не закрывает.
- Адресация по транспорту: реплика без Telegram-reply — реакция всем открытым обращениям чата;
  с reply — только тому, куда попал reply; reply мимо всех открытых (на закрытую работу или своё
  сообщение) — как без reply. Bitrix reply не передаёт, а модель при двух открытых обращениях почти
  всегда ставит номер одного — поэтому ссылке модели в первом слое не доверяют.
- `addition` и `correction` присоединяются к своей открытой работе (своя — где уже писал этот
  человек; ищется среди всех открытых); поправка до первой реакции сдвигает срок. Своей открытой
  работы нет, но своя работа закрылась не больше 10 минут назад и не ответом по существу — это
  продолжение своей речи, нового срока нет; иначе — новая просьба.
- **Оплата.** Реплика клиента с меткой `request`, которая по тексту — чистое подтверждение оплаты
  («Спасибо, оплатила», «оплачено», «Готово» в ответ на просьбу компании оплатить или подписать),
  обращения не открывает; платёжный файл того же автора в пределах 10 минут — часть подтверждения.
  С просьбой или вопросом («Оплатили, пришлите закрывающие», «оплатили?», «прошу», «нужно», «жду»,
  «но», «ошибка», «вернули») реплика остаётся обращением.
- **Отзыв до срока.** Клиент отозвал просьбу («вопрос решили», «отбой», «уже не требуется») до первой
  реакции и до её срока — «ответа не требовалось». Условия: открытое обращение одно, отзыв пишет его
  автор, метка отзыва — из белого списка (`ack`, `social`, `answer`, `info`, `offline`, `addition`,
  `correction`). После срока нарушение остаётся.
- `offline` («позвоню сам», «обсудим по телефону») ответа в чате не требует; но прямая просьба
  связаться в повелительной форме («перезвоните мне») с этой меткой — обращение со своим сроком.
- Подпись «(К) Имя» у интегратора — человек со стороны клиента (§5): его реплики движок читает
  как слова клиента.

**Второй слой — специалист.**

- Открывает передача (`handoff`) со ссылкой модели (`answers_request_id`) на обращение. Повтор
  передачи срок не продлевает.
- **Передача без ссылки** открывает второй слой, только когда угадывать не нужно: открытое обращение
  без передачи в чате одно, передача — его первая реакция и в нём нет реплики `offline`. При двух
  и больше открытых движок не угадывает.
- **Звонки.** По обращению, где все просьбы — позвонить, связаться или соединить (метка `offline`
  или текст), второй слой не открывается: звонок идёт вне чата. Первый слой судится как обычно.
  Если в той же реплике есть другая просьба («созвониться… и пришлите прайс»), слой открывается.
- Закрывает ожидание специалиста: ответ по существу или встречный вопрос клиенту со ссылкой
  на обращение; без ссылки — только при единственном ожидании в чате — выход на связь другого
  сотрудника (не того, кто передавал), в том числе **реплика специалиста** с меткой `other`;
  неопределённый автор после передачи — компания вышла на связь. Вердикт с пустым
  `is_substantive` второй слой не закрывает. Результат того, кто передавал, без ссылки не засчитывается.
- **Соседи по пачке** (обращения с одной первой реакцией): встречный вопрос со ссылкой на соседа,
  а также результат по существу другого специалиста засчитываются единственному ожиданию
  специалиста этой пачки, в том числе когда ссылка попала в уже закрытого соседа.
- **Отзыв при ожидании специалиста.** Клиент отозвал просьбу («не надо уже», «вопрос решился») при
  единственном открытом обращении, которое ждёт специалиста, — ожидание снимается («ответ
  не требовался») только до срока специалиста; после срока нарушение второго слоя остаётся. Метки —
  тот же белый список: «не надо уже, но пришлите акт» — новая просьба.

**Почему правила закреплены в коде, а не в настройках.** Метки модели на одном и том же входе
не полностью воспроизводимы, и эффект правки виден только на полной размеченной неделе переписки.
Любая правка поведения — сначала проверка на размеченной неделе, затем смена `ENGINE_RULES_REVISION`
и запись в [`CHANGELOG.md`](../CHANGELOG.md).

### 7.5 Версии настроек

Пороги первого и второго слоя, окна ожидания и рабочий календарь хранятся с историей
(`services/versioning.py`): правка сдвигает прежнее значение в историю, новое действует с момента,
который можно указать в боте. Каждое обращение считается по настройкам на момент открытия.
Без этого смена конца рабочего дня переписывала бы просрочки прошлых недель.

## 8. Алерты и рассылки

Код — `services/alerts.py`, `alert_digest.py`, `digest.py`. Правила и значения —
[`RULES.md`](RULES.md), раздел 8.

- Алерт по обращению — одна запись в `alert_log` на слой. Запись создаётся до отправки:
  сбой между отправкой и записью задвоил бы алерт. Доставка отмечается отдельно, недоставленное
  досылается следующими тиками (до 5 попыток), только тем, кому не дошло.
- По чату горит не больше одного алерта каждого слоя; новые просрочки пишутся как покрытые им.
  Горящий — отправленный получателям не раньше 48 часов назад (`STRIKE_MAX_AGE`), не покрытый
  и не зачёркнутый (`_open_alert_filters`).
  Серия просроченных обращений одной ветки в пределах порога схлопывается в одно.
- Закрытое обращение зачёркивает свой алерт в самом сообщении (в течение 48 часов).
  Алерт не зачёркивается, пока ждёт хоть одна покрытая им просрочка.
- Рассылки бронируют выпуск отдельной транзакцией до первого вызова Telegram: перезапуск
  не задваивает рассылку. Недоставленные выпуски досылаются до 3 раз.
- Если Telegram перевёл группу уведомлений в супергруппу, бот ловит ошибку миграции, запоминает
  новый номер в `setting` и досылает туда без правки конфигурации.

## 9. Доступ и роли

Код — `services/access.py`, проверка на каждое нажатие — `bot/middlewares.py`.

- Роли — пресеты прав (`ROLE_PRESETS`): владелец, администратор (права владельца без передачи
  владения), сотрудник (свои показатели и свои алерты). Отдельному пользователю можно добавить
  или убрать права поверх роли.
- Бот отвечает только активным учёткам. Незнакомцу — нейтральная фраза без намёка на систему доступа:
  бота видно в клиентских чатах, и `/start` может нажать клиент.
- Первый владелец — `BOOTSTRAP_OWNER_TG_ID`. Владелец в системе есть всегда: последнего нельзя
  понизить или отключить, роль только передаётся.
- Приглашение — одноразовая ссылка на 48 часов, в базе только хеш кода.

## 10. Живость и самодиагностика

- **Healthcheck** (`app/health.py`). Процесс сам пишет отметку `/tmp/heartbeat/<имя>.beat`
  после каждого круга работы; `python -m app.health bot|worker` проверяет её свежесть
  (бот — 600 с, worker — 300 с). Отметка в файле, а не в базе: база может лежать как раз тогда,
  когда проверка нужнее всего. Бот обновляет отметку на каждом апдейте и раз в минуту вызовом `getMe`.
- **Сторож живости.** Docker по статусу unhealthy контейнер не перезапускает. Поэтому отдельный поток
  (не asyncio-задача: зависнуть может сам цикл событий) раз в 30 с смотрит на ту же отметку
  и завершает процесс, если она протухла; дальше срабатывает `restart: unless-stopped`.
- **Простой.** Worker при старте сравнивает время с последним пульсом в базе; разрыв больше 5 минут —
  одно сообщение ответственным с границами простоя.
- **Экран «Состояние системы»** (`bot/handlers/health.py`) — версия сборки из `app/BUILD_INFO`,
  состояние ИИ, очередь, расход, пульс, блок «Неполадки», журнал действий. Условия очереди
  на экране и в worker общие — экран не может разойтись с тем, что worker реально обрабатывает.

## 11. Безопасность

- **Заслон на запись в группы** (`bot/guard.py`). Бот создаётся только фабрикой `create_bot`,
  каждый исходящий вызов проходит middleware. Для группового `chat_id` разрешены только читающие
  методы из белого списка; новый метод Bot API запрещён по умолчанию. Группе уведомлений разрешены
  `SendMessage`, `SendDocument` и `EditMessageText` (зачёркивание своих алертов). Правки
  по `inline_message_id` запрещены. Нарушение — исключение до сетевого запроса.
  Смоук `verify_no_group_reply.py` проверяет, что на теги, реплаи и команды в группах бот молчит.
- **Роль базы `botapp`** (`scripts/db_app_role.sql`). bot и worker ходят в базу ролью только с DML;
  DDL и учётные данные владельца схемы у них нет (`.env.app` без `DATABASE_URL`, `POSTGRES_PASSWORD`
  и пароля бэкапов `BACKUP_PASSPHRASE`).
  Права на будущие таблицы выдаются через `ALTER DEFAULT PRIVILEGES`.
- **Hardening compose.** `no-new-privileges`, `cap_drop: ALL`, `mem_limit 512m`, `pids_limit 256`,
  ротация логов (10 МБ × 5). Процесс в образе — непривилегированный пользователь. Порт базы
  на хост не публикуется: PostgreSQL доступен только внутри сети Compose-проекта по `postgres:5432`.
- **Секреты** — только в `.env` / `.env.app` с правами 600. Ключ провайдера меняется скриптом
  со скрытым вводом. Дампы шифруются при заданном `BACKUP_PASSPHRASE`.
- **Данные у провайдера ИИ.** Уходят тексты переписки с клиентами (с подписью сотрудника),
  без названий чатов и Telegram ID. Выбор провайдера — вопрос политики компании.
- **Хранение.** Журнал апдейтов старше 90 дней удаляется; тексты сообщений по умолчанию хранятся
  бессрочно (нужны для пересчёта разметки), срок настраивается в боте.

## 12. Тесты и проверки

- `tests/` — pytest; тесты с базой идут на отдельной базе из `TEST_DATABASE_URL`.
  Тесты движка с фиксированными датами обязаны передавать `now=`: пересборка берёт время с часов,
  и незапиненный тест стареет вместе с настоящим временем.
- `scripts/verify_*.py` — смоуки без Telegram: сборка диспетчера и всех кнопок, заслон по всем
  методам Bot API, молчание в группах, доступ к отчётам, обход всех читающих экранов.
- CI (`.github/workflows/ci.yml`): compileall, pytest, миграции на чистую базу + `alembic check`,
  ruff F821/F823, смоуки. Тот же набор гоняет гейт `deploy.sh` внутри нового образа.

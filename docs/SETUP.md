# Развёртывание с нуля

Инструкция для техника, который ставит бота на свой сервер. Каждый шаг содержит
команды и признак, что он удался. Что это за система —
[`ARCHITECTURE.md`](ARCHITECTURE.md), что делать после запуска —
[`OPERATIONS.md`](OPERATIONS.md).

Команды вводятся по одной или небольшими блоками, в Bash от root. `set -o pipefail`
показывает ошибку в начале конвейера. `set -e` в интерактивной сессии не включайте:
при первой ошибке он закроет сессию. Если команда завершилась ошибкой, остановитесь
и разберитесь, дальше не идите.

## 0. Что нужно на входе

| Что | Где взять |
|---|---|
| Linux-сервер: Ubuntu 22.04 или новее, 2 CPU, 4 ГБ памяти, от 20 ГБ диска | любой VPS; на общем сервере — не меньше 10 ГБ свободного места под образы, базу и бэкапы |
| Docker с плагином Compose v2.20+ | `docker compose version` должен работать |
| Пакеты `unzip`, `curl`, `openssl`; для обновления скриптом — `git` и `rsync` | `apt-get install -y unzip curl openssl git rsync` |
| Исходящий HTTPS к `api.telegram.org` и к API провайдера моделей; для сборки образа — к Docker Hub и PyPI | входящие порты не нужны: бот сам опрашивает Telegram |
| Telegram-бот и его токен | @BotFather → `/newbot` |
| Ключ OpenAI-совместимого провайдера, открывающий две модели: основную и резервную | по умолчанию настроен Cloud.ru Foundation Models: консоль → API-ключи |
| Числовой Telegram ID первого владельца бота | любой бот вида @userinfobot, или см. шаг 7 |
| Служебная группа для алертов (необязательно) | обычная группа Telegram, где сидят руководители |

Сотрудники компании должны писать в клиентские чаты через интегратор Bitrix24,
который подписывает сообщения как «Имя Фамилия [домен] пишет:». Бот работает и без
интегратора, но тогда сотрудников он узнаёт только по их Telegram-аккаунтам
(см. [`RULES.md`](RULES.md), раздел 4).

Переменная для команд ниже:

```bash
export BOT_DIR=/opt/chat-sla-bot
```

## 1. Настроить бота в BotFather

1. `/newbot`, сохранить токен.
2. `/mybots` → бот → Bot Settings → **Group Privacy → Turn off**. Иначе в группах
   бот видит только команды, а не переписку.
3. Права администратора в группах боту не нужны: его добавляют обычным участником.

## 2. Проверить сервер

Только чтение, ничего не меняет:

```bash
docker compose version
docker compose ls -a          # нет ли уже проекта с тем же именем
docker volume ls              # нет ли тома <имя проекта>_pgdata
df -h /opt "$(docker info --format '{{.DockerRootDir}}')"
curl -sS -I --max-time 15 https://api.telegram.org
curl -sS -I --max-time 15 https://foundation-models.api.cloud.ru/v1/models
```

Любой HTTP-ответ, включая 302 и 404, значит, что сервер доступен по HTTPS. Таймаут
до Telegram надо устранить до запуска.

Имя Compose-проекта задано в `docker-compose.yml` (строка `name:`), от него зависят
имена контейнеров и тома с базой. Если такое имя на сервере уже занято, задайте
в `.env` своё `COMPOSE_PROJECT_NAME` **до первого запуска** и больше его не меняйте:
смена имени у работающей установки создаст новую пустую базу. Порт базы на хост
не публикуется, поэтому существующий PostgreSQL на порту 5432 не мешает.

Никогда не выполняйте в каталоге бота `docker compose down -v`, `docker volume prune`
и `docker system prune`: первые две команды удаляют базу.

## 3. Разложить код

```bash
sudo -i
set -o pipefail
umask 077
test ! -e "$BOT_DIR" && echo 'Каталог свободен' || echo 'Каталог уже есть: остановиться и проверить'
install -d -m 700 "$BOT_DIR"
cd "$BOT_DIR"
git clone <адрес репозитория> .      # или распаковать архив с кодом
chmod +x scripts/*.sh
mkdir -p backups logs
```

Признак: `ls` показывает `app alembic scripts docs docker-compose.yml`.

## 4. Заполнить `.env`

```bash
cp .env.example .env && chmod 600 .env
nano .env
```

Каждая переменная описана комментарием в `.env.example`. Обязательно заполнить:

| Переменная | Что вписать |
|---|---|
| `BOT_TOKEN` | токен от BotFather |
| `BOOTSTRAP_OWNER_TG_ID` | числовой Telegram ID первого владельца; можно заполнить позже (шаг 7) |
| `POSTGRES_PASSWORD` | пароль владельца схемы: `openssl rand -hex 24` |
| `DATABASE_URL` | `postgresql+asyncpg://botuser:<POSTGRES_PASSWORD>@postgres:5432/chatstats` |
| `APP_DATABASE_URL` | `postgresql+asyncpg://botapp:<пароль botapp>@postgres:5432/chatstats`; пароль botapp — ещё один `openssl rand -hex 24` |
| `AI_API_KEY` | ключ провайдера моделей |
| `EPISODE_RULES_V4_SINCE` | в шаблоне уже `2026-01-01T00:00:00+00:00`; подойдёт любой момент раньше первого сообщения, с часовым поясом |
| `BACKUP_PASSPHRASE` | пароль шифрования бэкапов: `openssl rand -hex 32`; раскомментировать строку |

Пароли — только латинские буквы и цифры: `.env` читают и bash, и Docker Compose,
а кавычки и спецсимволы они разбирают по-разному. Пароли входят в строки
подключения, поэтому хост в DSN — `postgres`, а не `localhost`. `BACKUP_PASSPHRASE`
сохраните отдельно от сервера: без него зашифрованные бэкапы не расшифровать.

**Две переменные решают, работает ли разметка вообще:**

- `AI_ENABLED=true` — классификация моделью включена;
- `AI_SHADOW_MODE=false` — вердикты модели учитываются. При `true` модель вызывается,
  вердикты пишутся, но на обращения и алерты не влияют. В коде значение
  по умолчанию `true`, поэтому строка `AI_SHADOW_MODE=false` в `.env` обязательна.

**Границы версий правил.** Движок обращений считает обращение по версии правил,
действовавшей в момент его открытия (подробно — [`ARCHITECTURE.md`](ARCHITECTURE.md), 7.3).
Для новой установки достаточно `EPISODE_RULES_V4_SINCE` с моментом раньше первого
сообщения: v4 включает правила v2 и v3. Если все три границы пусты, движок считает
по самым первым правилам v1. Однажды заданную границу не сдвигайте: это пересчитает
историю обращений.

**Что можно оставить как в шаблоне:** адрес провайдера и модели (`AI_BASE_URL`,
`AI_MODEL`, `AI_FALLBACK_MODEL` и их профили промптов), месячный потолок токенов,
цены для расчёта расхода в рублях, `TZ`, `ALLOWED_UPDATES`. `AI_PREVIOUS_MODELS`
в шаблоне пуст: разметки прежних моделей в базе ещё нет. Сменив модель, допишите сюда прежнюю.

**Что заполнить позже:**

- `INTEGRATOR_BOT_ID` — ID бота-интегратора Bitrix24 в ваших чатах. Если не уверены
  в значении, оставьте пустым и узнайте на шаге 8.
- `NOTIFY_GROUP_CHAT_ID` — ID служебной группы для алертов, шаг 9. Без неё алерты
  и отчёты приходят только в личку.

Соберите `.env.app` — тот же файл без учётных данных владельца схемы и пароля
бэкапов. Его читают `bot` и `worker`, `.env` — только миграции и скрипты бэкапа:

```bash
grep -vE '^(DATABASE_URL|POSTGRES_PASSWORD|BACKUP_PASSPHRASE)=' .env > .env.app && chmod 600 .env.app
docker compose config --quiet     # проверка без вывода секретов
```

Эту команду сборки `.env.app` повторяйте после **каждой** правки `.env`.

## 5. Проверить ключ провайдера

Проверка делает настоящий запрос генерации к обеим моделям и не печатает ключ:

```bash
set -a; . ./.env; set +a
for m in "$AI_MODEL" "$AI_FALLBACK_MODEL"; do
  code=$(curl -s -o /tmp/ai_check.json -w '%{http_code}' --max-time 60 "$AI_BASE_URL/chat/completions" \
    -H "Authorization: Bearer $AI_API_KEY" -H "Content-Type: application/json" \
    -d "{\"model\":\"$m\",\"messages\":[{\"role\":\"user\",\"content\":\"ping\"}],\"max_tokens\":5}")
  echo "$m: HTTP $code"; head -c 300 /tmp/ai_check.json; echo
done
rm -f /tmp/ai_check.json
```

Признак: для обеих моделей HTTP 200 и JSON с полем `choices`. 401 или 403 — ключ
неверен или без прав, 402 — не хватает денег на балансе, 404 — модель недоступна
этому ключу или имя указано неверно. Запрос `GET /models` для такой проверки
не годится: он может отвечать 200 даже без ключа.

## 6. Поднять базу и запустить

```bash
docker compose up -d --wait --wait-timeout 120 postgres
docker compose run --rm migrate
set -a; . ./.env; set +a
docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
  -v app_password='<пароль botapp из APP_DATABASE_URL>' -v dbname="$POSTGRES_DB" \
  < scripts/db_app_role.sql
docker compose up -d
```

`migrate` создаёт схему и завершается. `scripts/db_app_role.sql` создаёт роль
`botapp` с правами только на строки таблиц; скрипт можно запускать повторно,
он обновит пароль и права.

Признак через 1–2 минуты:

```bash
docker compose ps                         # bot и worker — (healthy)
docker compose logs --tail 50 bot worker  # в логе worker есть строка worker.starting
```

Если `migrate` упал, `bot` и `worker` не запустятся: разберитесь по его выводу.
Если контейнер `unhealthy` или перезапускается — `docker compose logs --tail 100 bot`;
типичные причины: пустой `BOT_TOKEN`, неверный DSN, нет сети до `api.telegram.org`.

## 7. Первый вход

Человек с Telegram ID из `BOOTSTRAP_OWNER_TG_ID` пишет боту `/start` в личку и сразу
получает роль владельца и главное меню.

Если ID заранее не знали: владелец пишет боту `/start`, получает нейтральный ответ
«Здравствуйте. Этот бот не ведёт переписку.», а его ID появляется в базе:

```bash
docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c \
  "SELECT tg_user_id, username, display_name FROM bot_user ORDER BY id DESC LIMIT 5;"
```

Владельцем назначается только тот, кого бот видит впервые, поэтому запись
с заявкой нужно убрать. Затем впишите ID в `BOOTSTRAP_OWNER_TG_ID`, пересоберите
`.env.app` (шаг 4), перезапустите процессы и снова напишите боту `/start`:

```bash
docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c \
  "DELETE FROM bot_user WHERE tg_user_id = <ID>;"
docker compose up -d --force-recreate bot worker
```

Остальные люди получают доступ по одноразовой ссылке-приглашению или по заявке,
которую одобряет владелец: «🛡 Пользователи бота» ([`SCREENS.md`](SCREENS.md), раздел 7).

## 8. Подключить чаты и интегратор

1. Добавьте бота обычным участником в клиентские чаты. Новый чат сразу попадает
   в анализ (это настройка, её можно выключить). Историю до своего добавления бот
   не видит.
2. Попросите сотрудника написать в любой из этих чатов из Bitrix24.
3. Откройте «🩺 Состояние системы». Если `INTEGRATOR_BOT_ID` не задан или неверен,
   в блоке «Неполадки» будет строка «В чатах пишет неизвестный бот» с его ID.
4. Впишите этот ID в `INTEGRATOR_BOT_ID`, пересоберите `.env.app` и выполните
   `docker compose up -d --force-recreate bot worker`. Worker сам пересчитает
   стороны всех уже собранных сообщений.

Признак: на экране состояния нет строки про неизвестного бота, справочник
«👥 Сотрудники» начал пополняться именами из подписей.

## 9. Служебная группа уведомлений (по желанию)

1. Создайте группу для руководителей и добавьте туда бота.
2. Отправьте в группу любое сообщение и найдите её ID (у супергрупп он вида `-100…`):

   ```bash
   docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c \
     "SELECT tg_chat_id, title FROM chat ORDER BY id DESC LIMIT 5;"
   ```

3. Впишите ID в `NOTIFY_GROUP_CHAT_ID`, пересоберите `.env.app`,
   `docker compose up -d --force-recreate bot worker`.
4. В «💬 Чаты» уберите эту группу в архив и удалите: она успела попасть в список
   как обычный чат. Дальше её сообщения не сохраняются.

Это единственная группа, куда боту разрешено писать. Она задаётся только
конфигурацией сервера, кнопкой её не поменять: иначе алерты можно было бы
направить в клиентский чат. Если Telegram переведёт группу в супергруппу и сменит
её ID, бот запомнит новый номер сам.

## 10. Включить алерты и рассылки

На чистой базе алерты и рассылки выключены: сначала нужно убедиться, что стороны
и авторы определяются верно. Проверьте в «⚙️ Настройки»:

- «🕐 Рабочий календарь» — рабочие дни, начало и конец дня, часовой пояс, праздники.
  Часовой пояс календаря должен совпадать с `TZ` в `.env`
  (см. [`RULES.md`](RULES.md), раздел 11);
- «🔔 Алерты» — порог первой реакции, срок специалиста; затем включить «Отправка
  алертов» и, если нужно, «Алерты «нет ответа специалиста»» и «Алерты в группу
  уведомлений»;
- «📮 Отчёты по расписанию» — нужные блоки.

## 11. Бэкапы

Добавьте две строки в `crontab -e`, не трогая задания других приложений. Время —
в часовом поясе сервера (`timedatectl`):

```cron
# Бэкап базы ежедневно в 03:20, хранение 14 дней
20 3 * * * cd /opt/chat-sla-bot && ./scripts/backup.sh >> /opt/chat-sla-bot/backups/backup.log 2>&1
# Проверка восстановления по воскресеньям в 04:10
10 4 * * 0 cd /opt/chat-sla-bot && ./scripts/restore_test.sh >> /opt/chat-sla-bot/backups/restore.log 2>&1
```

Признак на следующий день: последняя строка `backups/backup.log` начинается с `OK`.
Копии лежат на том же диске — это защита от ошибки в базе, а не от потери сервера.
Вывоз копий за пределы сервера настройте отдельно.

## 12. Итоговая проверка

- `docker compose ps`: `bot` и `worker` — `healthy`.
- «🩺 Состояние системы»: строка «ИИ: включён»; через 5–10 минут «Провайдер ИИ:
  последний живой контакт» и «Классификация: последний вердикт» показывают свежее
  время, «Очередь разметки» убывает до «пусто», пульс фонового обработчика
  не старше нескольких минут.
- Блок «Неполадки» пуст или содержит только ожидаемое.
- Проверка без Telegram (смоуки: сборка диспетчера, кнопки, права, заслон):

  ```bash
  docker compose run --rm --no-deps -v "$PWD/scripts:/app/scripts" -e PYTHONPATH=/app \
    bot python scripts/verify_bot.py
  ```

Проверяйте сценарии в отдельном тестовом чате, не в клиентских: тестовые сообщения
попадут в показатели и алерты. Не запускайте второй экземпляр бота на том же токене:
Telegram отдаёт каждое сообщение только одному получателю.

## 13. Тесты локально

Тестам нужна отдельная база PostgreSQL:

```bash
pip install -r requirements-dev.txt
TEST_DATABASE_URL=postgresql+asyncpg://user:pass@localhost:5432/chatstats_test python -m pytest
```

Без `TEST_DATABASE_URL` тесты с базой пропускаются. Тот же набор гоняет CI
(`.github/workflows/ci.yml`) и гейт `scripts/deploy.sh` перед выкаткой.

## Приложение: переменные окружения

Полный список — `app/config.py`, комментарии — `.env.example`.

| Переменная | По умолчанию в коде | Что это |
|---|---|---|
| `BOT_TOKEN` | — | токен бота |
| `BOOTSTRAP_OWNER_TG_ID` | — | кто станет владельцем при первом `/start` |
| `INTEGRATOR_BOT_ID` | — | ID бота-интегратора Bitrix24; смена пересчитывает стороны всей истории |
| `NOTIFY_GROUP_CHAT_ID` | — | единственная группа, куда бот пишет |
| `ALLOWED_UPDATES` | `message,edited_message,callback_query,my_chat_member,chat_member` | типы апдейтов; без `callback_query` кнопки не работают |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | — | владелец схемы и база для сервиса `postgres` |
| `DATABASE_URL` | — | DSN владельца схемы: миграции, бэкапы |
| `APP_DATABASE_URL` | — | DSN роли `botapp` для bot и worker; пусто — они ходят под `DATABASE_URL` |
| `AI_ENABLED` | `false` | включить классификацию моделью |
| `AI_SHADOW_MODE` | `true` | вердикты модели пишутся, но не влияют на обращения; в рабочем `.env` — `false` |
| `AI_BASE_URL`, `AI_MODEL`, `AI_API_KEY` | — | адрес OpenAI-совместимого API, основная модель, ключ |
| `AI_PROMPT_PROFILE` | по имени модели | профиль промпта из `app/services/ai.py` |
| `AI_FALLBACK_MODEL`, `AI_FALLBACK_PROMPT_PROFILE` | — | резервная модель и её профиль; пусто — резерва нет |
| `AI_PREVIOUS_MODELS` | — | модели, чья разметка в базе остаётся действительной; не сокращать на работающей установке |
| `AI_MONTHLY_TOKEN_LIMIT` | без потолка | месячный потолок токенов |
| `AI_PRICE_IN_PER_M`, `AI_PRICE_OUT_PER_M` | — | цена миллиона токенов в рублях для экрана состояния |
| `AI_TIMEOUT_SECONDS` | 60 | таймаут одного вызова |
| `AI_SLOW_LATENCY_SECONDS`, `AI_SLOW_QUEUE_MINUTES` | 10, 15 | пороги состояния «провайдер медленный» |
| `AI_FALLBACK_RETRIES`, `AI_FALLBACK_RETRY_WINDOW_SECONDS` | 3, 300 | сколько отказов основной за какое окно переводят на резерв |
| `AI_FALLBACK_PROBE_SECONDS`, `AI_FALLBACK_RESTORE_SUCCESSES` | 1800, 2 | как часто пробовать основную на резерве и сколько удачных проб её возвращают |
| `TZ` | `Europe/Moscow` | часовой пояс контейнеров, логов и части отчётов |
| `LOG_LEVEL` | `INFO` | уровень логов |
| `ENVIRONMENT` | `dev` | метка окружения на экране состояния |
| `EPISODE_RULES_V2_SINCE`, `EPISODE_RULES_V3_SINCE`, `EPISODE_RULES_V4_SINCE` | — | границы версий правил движка; не сдвигать |
| `BACKUP_PASSPHRASE` | — | пароль шифрования дампов; не попадает в `.env.app` |
| `COMPOSE_PROJECT_NAME` | из `docker-compose.yml` | имя Compose-проекта; задавать только до первого запуска |

Бизнес-настройки — календарь, пороги, рассылки, сроки хранения — в `.env` не живут:
они хранятся в базе и меняются кнопками в боте.
